# F11 — Entrega local

Plano e registro da F11 (`docs/escopo.md` §12). *Pronto quando*: um clone limpo roda a
demo com dois comandos: `docker compose up` sobe Postgres, API, worker e os três
simuladores, e o script de demo conta o roteiro GameStore (PIX, liquidação, chargeback).

## 1. O que já existe

- `compose.yaml` com só o Postgres, que o `mise run db` sobe para o desenvolvimento.
- Os sete binários (`api`, `worker`, `pixsim`, `cardsim`, `boletosim`, `migrate`,
  `admin`), cada um configurado só por variáveis de ambiente.
- `GET /healthz` na API e nos simuladores, e `GET /readyz` na API, que pinga o banco.
- O `e2e/`, que já sobe tudo como processos, e o `mise.toml` com os segredos de dev.

## 2. Decisões propostas

1. **Uma imagem.** Um `Dockerfile` multi-stage compila os sete binários numa imagem
   `distroless/static` sem root; cada serviço do compose escolhe o seu comando.
   *Descartado:* uma imagem por binário: sete builds do mesmo módulo, e um `go build`
   que já compila tudo de uma vez.
2. **Compose.** O `compose.yaml` ganha `migrate` (roda uma vez, depois do Postgres
   saudável), `api` e `worker` (depois do `migrate` terminar) e os três simuladores. As
   portas ficam em `127.0.0.1`, e os segredos são os de dev do `mise.toml`, marcados como
   tal. O `mise run db` passa a subir só o `postgres`.
   *Descartado:* um segundo arquivo de compose para a demo: dois lugares para manter os
   mesmos serviços.
3. **Esperar os serviços.** A imagem distroless não tem `curl`, então não há healthcheck
   nos serviços Go; quem espera é a demo, que consulta `/readyz` e os `/healthz` antes de
   começar.
   *Descartado:* um modo `-healthcheck` em cada binário só para o compose: código de
   produção para a infraestrutura de uma demo.
4. **Demo em Go.** `cmd/demo`, na mesma imagem, roda com
   `docker compose run --rm demo`: cria a GameStore pelo `admin`, registra um endpoint de
   webhook que a própria demo serve, e narra cada passo com os valores (US$, R$, taxa,
   líquido). Assim o segundo comando não depende de `curl` nem de `jq` na máquina de quem
   clona.
   *Descartado:* um script `sh` com `curl`: mais curto, mas precisa de ferramentas no host
   e não tem teste.
5. **Roteiro da demo:**
   - PIX de US$ 20,00: a cobrança com o BR Code de R$ 101,50, o pagador paga pelo
     simulador, o webhook `payment.paid` chega assinado e o saldo mostra US$ 19,40;
   - liquidação: o saldo `pending` e a data de corte em que ele vira `available` e é pago;
     o PIX liquida em D+1 (decisão 52), então a demo não espera o payout acontecer;
   - cartão de US$ 15,00 capturado, chargeback aberto pelo adquirente, a GameStore
     contesta, o emissor decide a favor, e o saldo volta.
6. **Teste da demo.** Um teste no `e2e/` roda o binário da demo contra o stack de
   processos e quer saída 0, então a demo quebra no CI junto com o que ela mostra. Um job
   no CI faz o caminho de quem clona: `docker compose up -d` e
   `docker compose run --rm demo`.

  *Descartado:* `SETTLEMENT_PIX_DAYS=0` no compose da demo: mostraria o payout de verdade,
  com uma configuração de produção só para ela.

  PR, porque é o único teste do caminho de quem clona.
